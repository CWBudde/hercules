# SAFE-01 remote cache safety verification

Date: 2026-07-25
Status: completed

## Cache ownership and replacement contract

Remote disk caches now use a managed-directory policy:

- Hercules clones into a randomly named temporary sibling of the requested cache path.
- The staging directory receives a versioned `.hercules-cache` ownership marker before cloning.
- A failed clone removes only that marked staging directory and leaves the requested destination
  untouched.
- A missing destination is installed with an atomic no-replace rename.
- An existing empty destination is replaced only through atomic directory exchange.
- An existing non-empty destination requires both `--force-cache-replace` and an exact, regular
  Hercules marker. The marker is checked before cloning and again immediately before exchange.
- The replaced directory is recursively removed only after the atomic exchange, only when force
  was explicit, and only after its Hercules marker is verified at the exchanged staging path.
- Unrelated directories, symbolic links, filesystem roots, the current working directory, and the
  user's home directory are rejected.
- Filesystem inspection errors other than a genuinely missing destination are returned as hard
  errors.

Linux uses `renameat2` with `RENAME_NOREPLACE` and `RENAME_EXCHANGE`. macOS uses `renameatx_np`
with `RENAME_EXCL` and `RENAME_SWAP`. Windows uses its non-replacing directory rename for a new
cache; because it has no equivalent directory-exchange primitive here, replacement of an existing
cache returns a hard error and leaves the original path untouched. Other unsupported platforms
follow the same fail-closed behavior.

The installed cache remains a valid bare Git repository and can be reopened through the documented
`hercules /path/to/cache` workflow.

## Regression coverage

`cmd/hercules/root_test.go` covers:

- creating and reopening a new marked cache;
- an existing empty destination;
- an existing managed cache with and without explicit force;
- an unrelated directory containing sentinel data, including a force attempt;
- filesystem root, current working directory, and home directory rejection;
- a failed clone preserving the previous marked cache and sentinel;
- an injected atomic replacement failure preserving the previous cache;
- filesystem inspection failures returning errors.

The reusable cross-platform workflow runs this safety group on `ubuntu-latest`, `macos-latest`, and
`windows-latest`. The platform-specific implementations were also cross-compiled locally for
Darwin and Windows.
